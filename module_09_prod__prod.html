Деплой: выводим Django-проект «в бой»

В туториалах сайт живёт на runserver — это отладочный сервер разработки: медленный,
один процесс, не рассчитан на реальных пользователей и не защищает от внешних угроз.
Прод — это когда сайт работает в интернете, под своим доменом, через FastCGI/WSGI-сервер
и настоящую базу данных. Здесь — по шагам: от выбора окружения до автодеплоя в CI.

# Быстрый чек, что у вас есть
python3 --version   # 3.x (Django 6.x требует 3.12+)

Где вообще живёт Django в проде

В проде Django никогда не слушает HTTP сам. Запрос приходит так:

1. Веб-сервер (Nginx) принимает соединение снаружи, отдаёт статику (CSS, JS, картинки)
и проксирует остальные запросы дальше.
2. WSGI/ASGI-сервер (Gunicorn, uvicorn − для асинхронности) запускает несколько
готовых процессов Django и распределяет между ними запросы.
3. База данных — отдельный сервис (у нас PostgreSQL), к которому Django обращается
по сети, а не файлом.

Python-серверВеб-сервер перед ним
Рольисполняет код Djangoпринимает HTTP снаружи
ПримерыGunicorn, uvicorn, DaphneNginx, Caddy, Apache
СтатикаНЕ умеет отдавать хорошоотдаёт мгновенно + кэш
HTTPSтолько через терминирование на Nginxтерминирует TLS сам

Django Girls: после «деплоя» на Heroku-подобном хостинге такое разделение за вас делает
платформа. Мы же делаем всё сами — это тоже прокачка.

PostgreSQL вместо SQLite

SQLite — база «на диске», работает для одного процесса и не любит одновременных записей.
В проде выбираем полноценный сервер БД. Стандарт — PostgreSQL.

Ставим драйвер и подключаем

pip install psycopg          # официальный драйвер PostgreSQL для Python

В settings.py (DATABASES) заменяем SQLite на PostgreSQL:

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "mydb",
        "USER": "django",
        "PASSWORD": "секрет",         # см. раздел «Безопасность» (.env)
        "HOST": "127.0.0.1",          # или имя контейнера "db" в docker compose
        "PORT": "5432",
    }
}

Отличия от SQLite (важные)

  • Слушает порт 5432, подключение по сети, а не файлу.
  • Миграции те же команды: python manage.py migrate.
  • Пароль, HOST и PORT не должны лежать в репозитории (см. .env ниже).
  • Резервная копия делается утилитой pg_dump, а не копированием .db файла.
# Создать БД и пользователя (пример для Ubuntu-сервера с PostgreSQL 16)
sudo -u postgres psql -c "CREATE USER django WITH PASSWORD 'секрет';"
sudo -u postgres psql -c "CREATE DATABASE mydb OWNER django;"

# Проверить подключение Django
python manage.py migrate

Если база и Django «глушат» друг друга — сначала проверьте, что сервис поднят
(systemctl status postgresql) и разрешён порт/пароль. Ошибки подключения почти всегда
про левый HOST, несовпадение пароля или выключенную службу.

Статика и медиа в проде

Скорее всего, у вас уже есть static/ (CSS, JS) и, возможно, картинки пользователей
(media/). На runserver Django отдаёт их сам — в проде НЕ должен. Всю статику отдаёт Nginx.

python manage.py collectstatic --noinput   # собрать статику в STATIC_ROOT
# settings.py
import os
from pathlib import Path
BASE_DIR = Path(__file__).resolve().parent.parent

STATIC_URL = "/static/"
STATIC_ROOT = os.path.join(BASE_DIR, "staticfiles")   # куда collectstatic кладёт файлы

MEDIA_URL = "/media/"
MEDIA_ROOT = os.path.join(BASE_DIR, "media")          # загруженные фото/файлы

А Nginx уже отдаёт эти папки напрямую (пример конфига — ниже, секция «Деплой классика»).

WSGI и ASGI: в чём разница

WSGI — синхронный стандарт: на каждый запрос один процесс/поток. Этого достаточно для
подавляющего большинства сайтов.

ASGI — асинхронный: один процесс обрабатывает много запросов одновременно. Нужен для
WebSockets (чат, уведомления) и для async def-представлений.

Выбираем так:

ЗадачаWSGI (Gunicorn)ASGI (uvicorn / Daphne)
Обычный сайт, формы, база✔ стандарттоже можно
WebSockets, SSE, чат✘ не умеет✔ нужен именно он
async def-страницы✘✔

Django умеет и то и другое. Если большинство представлений обычные def — берите WSGI.
Потребовались WebSockets/async — переходите на ASGI, код моделей и шаблонов почти не меняется.

Пример async def-представления (работает только при ASGI-сервере):

# app/views.py
async def counter(request):
    # длинный запрос к внешнему API условно ждёт без блокировки других воркеров
    import asyncio
    await asyncio.sleep(0.01)
    return render(request, "app/counter.html", {"n": 1})

На WSGI такой код упадёт или заблокирует процесс — запомните маркер: если в коде
async def и await во view-слое — нужен ASGI-сервер.

Gunicorn умеет работать в ASGI-режиме через --worker-class uvicorn.workers.UvicornWorker,
так что менеджер процессов один и тот же, отличаются только воркеры.

pip install gunicorn uvicorn
# WSGI
gunicorn config.wsgi --bind 127.0.0.1:8000 --workers 3
# ASGI (те же команды рестарта/логов, другой worker-class)
gunicorn config.asgi --worker-class uvicorn.workers.UvicornWorker --bind 127.0.0.1:8000

Деплой «классика»: VPS + Gunicorn + Nginx

Полное разделение сервисов, полностью под вашим контролем. Схема:

 Браузер  →  Nginx :80/:443 (HTTPS, статика)
                      │
                      └── прокси → 127.0.0.1:8000 → Gunicorn (3 воркера) → Django
 База PostgreSQL слушает 127.0.0.1:5432 (только локально!)

1. Gunicorn слушает локальный адрес

Обратите внимание: Gunicorn НЕ должен быть виден снаружи — --bind 127.0.0.1:8000,
а не 0.0.0.0. Снаружи его «прикрывает» Nginx.

pip install gunicorn
# 3 воркера — разумный дефолт для небольшого проекта
gunicorn --bind 127.0.0.1:8000 --workers 3 myproject.wsgi:application

2. systemd-служба: сайт живёт после перезагрузки сервера

Файл /etc/systemd/system/gunicorn.service:

[Unit]
Description=Gunicorn instance — my django site
After=network.target

[Service]
User=django
Group=django
WorkingDirectory=/home/django/myproject
Environment="PATH=/home/django/myproject/venv/bin"
ExecStart=/home/django/myproject/venv/bin/gunicorn --bind 127.0.0.1:8000 --workers 3 config.wsgi:application

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now gunicorn      # автозапуск при загрузке сервера
sudo systemctl status gunicorn            # смотреть статус
sudo journalctl -u gunicorn -f            # смотреть логи в реальном времени

3. Nginx: HTTPS и статика

Конфиг /etc/nginx/sites-available/mysite:

server {
    listen 80;
    server_name mydomain.ru www.mydomain.ru;

    # Статика и медиа отдаём напрямую, минуя Django
    location /static/ { alias /home/django/myproject/staticfiles/; }
    location /media/  { alias /home/django/myproject/media/; }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo ln -s /etc/nginx/sites-available/mysite /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

Важно про заголовки (они пригодится и в безопасности): Django считает, что запрос
идёт напрямую к нему. Через эти proxy_set_header мы честно передаём реального посетителя.

# settings.py — включить, когда сайт за Nginx/HTTPS
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True

Без этих настроек Django не узнает о HTTPS и построит неверные ссылки.

4. HTTPS (Let's Encrypt)

Бесплатные сертификаты на русском просто: утилита certbot сама правит конфиг Nginx
и продлевает сертификаты. После первого выпуска добавляет редирект с HTTP на HTTPS.

sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d mydomain.ru -d www.mydomain.ru
# продление автоматическое через systemd-таймер certbot

Docker Compose: весь прод одной командой

Альтернатива «классике» — всё в контейнерах: приложение, PostgreSQL, Nginx.
Плюс: одинаковое окружение на любой машине и на сервере. Минус: чуть больше понятий.

Структура

myproject/
├── config/            # settings.py, urls.py (там же wsgi.py / asgi.py)
├── app/               # ваше приложение Django
├── requirements.txt
├── Dockerfile
└── docker-compose.yml

Dockerfile

FROM python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Сначала только зависимости (кэш слоя: код меняется чаще, чем requirements.txt)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000"]

docker-compose.yml

services:
  django:
    build: .
    volumes:
      - static_data:/app/staticfiles
    expose:
      - "8000"            # только внутри сети compose
    environment:
      - DJANGO_DEBUG=0
      - POSTGRES_HOST=db  # имя сервиса, НЕ localhost!
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=django
      - POSTGRES_PASSWORD=секрет
      - POSTGRES_DB=mydb
    volumes:
      - pgdata:/var/lib/postgresql/data   # данные переживают пересоздание контейнера

  nginx:
    image: nginx:1.27-alpine
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - static_data:/static:ro
    ports:
      - "80:80"
    depends_on:
      - django

volumes:
  pgdata:
  static_data:

Nginx в compose отдаёт статику из общего static_data-тома и проксирует всё остальное
на сервис django (имя = адрес в compose-сети):

server {
    listen 80;

    location /static/ { alias /static/; }

    location / {
        proxy_pass http://django:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Команды

docker compose up -d                 # собрать и запустить всё
docker compose exec django python manage.py migrate
docker compose exec django python manage.py collectstatic --noinput
docker compose logs -f               # логи всех сервисов
docker compose down                  # остановить (данные pgdata сохраняются)
docker compose build django          # пересобрать после правок кода

Мини-шпаргалка по compose — в разделе «Документация» (Docker для Django); здесь показан
именно прод-вариант с Nginx и томами для данных.

Деплой за вас: PaaS

Иногда хочется без администрирования одного сервера. Тогда сервисы Platform as a Service
сами собирают и запускают ваше приложение, дают HTTPS и БД:

СервисЧто даёт «бесплатно»
RenderGitHub-деплой, PostgreSQL, temp free-тир
Railwayпростой App + БД, деплой из репозитория
Fly.ioглобальный деплой Docker, платный минуты
Yandex Cloud / Timeweb Cloudроссийские площадки, VPS или PaaS-контейнеры

Общая идея: кладёте проект в GitHub, подключаете сервис к репозиторию, и он сам ставит
зависимости, мигрирует БД и обновляет сайт после каждого git push. Dockerfile выше —
это и есть типовой «контракт», который понимают такие платформы.

CI/CD: чтобы git push = деплой

CI/CD (Continuous Integration / Continuous Delivery) — автоматизация: после каждого пуша
сервер действий прогоняет тесты и, если всё зелёное, выкатывает сайт. Самый популярный —
GitHub Actions (бесплатный для opensource).

Файл .github/workflows/deploy.yml:

name: deploy
on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: python manage.py test        # тесты — «зелёный свет» на деплой

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: python manage.py collectstatic --noinput
      # Здесь: загрузка на ваш сервер (ssh + rsync) или push в PaaS.
      # Для GitHub Pages, как у этого сайта, хватает шагов выше.
      - uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./site

Секреты (пароли, токены SSH) хранятся в настройках репозитория → Settings → Secrets,
в коде их не должно быть. GitHub сам подставляет их при запуске пайплайна.

Минимум для старта: тесты обязательны — деплоить непроверенный код на прод — боль.

Безопасность: обязательный минимум

1. Пароли и настройки не в коде (.env)

Файл .env — локальный, в .gitignore. В нём секреты, которые различаются между
окружениями:

# .env (НЕ отправлять в git!)
DJANGO_SECRET_KEY=...
DJANGO_DEBUG=0
POSTGRES_PASSWORD=секрет
# settings.py
import os
from dotenv import load_dotenv
load_dotenv()

SECRET_KEY = os.getenv("DJANGO_SECRET_KEY")
DEBUG = os.getenv("DJANGO_DEBUG", "0") == "1"
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.getenv("POSTGRES_DB", "mydb"),
        "USER": os.getenv("POSTGRES_USER", "django"),
        "PASSWORD": os.getenv("POSTGRES_PASSWORD"),
        "HOST": os.getenv("POSTGRES_HOST", "127.0.0.1"),
        "PORT": "5432",
    }
}
pip install python-dotenv

Если секрет всё же попал в git — считайте его скомпрометированным: поменяйте и
перепишите историю (или просто меняйте секрет как минимум).

2. DEBUG = False — всегда на проде

DEBUG=1 на проде — катастрофа: на любой ошибке кто угодно увидит полный трейсбек,
строки кода, переменные, пароли и непокрытые URL. Секрет, ALLOWED_HOSTS, отладчик —
всё наружу.

# обязательная настройка при DEBUG=False
ALLOWED_HOSTS = ["mydomain.ru", "www.mydomain.ru"]

Пустой или заблокированный host приведёт к отказу (это и есть защита от fake Host-заголовка).

3. Безопасные HTTP-заголовки (middleware)

В финальных версиях Django безопасные заголовки включены по умолчанию в
MIDDLEWARE (в свежем проекте они уже там). Проверьте в settings.py:

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",   # HSTS, X-Content-Type-Options
    # ... остальные
]

Важные настройки под ними:

SECURE_SSL_REDIRECT = True               # редирект на HTTPS
SESSION_COOKIE_SECURE = True             # cookie только по HTTPS
CSRF_COOKIE_SECURE = True
SECURE_HSTS_SECONDS = 31536000           # заставить браузер ходить только по HTTPS

4. Файервол и доступы

# Пропускаем только 80, 443 и SSH (пример для ufw) — никакой 8000 наружу!
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

8000 должен быть доступен только локально/в compose-сети. Открытый наружу
Gunicorn/Django — типичная дыра (нет HTTPS, уязвим к spoofing-заголовкам).

5. Чек-лист перед деплоем

python manage.py check --deploy    # встроенный аудит (выведет список рекомендаций)
python manage.py test              # все тесты зелёные
python manage.py migrate           # последние миграции на прод-базе
python manage.py collectstatic --noinput

check --deploy не решает проблемы за вас, но перечисляет незакрытые места
(HTTP, cookies без Secure, слабый SECRET_KEY и т.п.) по пунктам.

Практический план «с нуля до проды»

1. Локально: переключили БД на PostgreSQL, вынесли секреты в .env,
включили ALLOWED_HOSTS, выключили DEBUG.
2. Статика: collectstatic работает, папка в .gitignore (генерируется заново).
3. Сервер: купили VPS, настроили SSH-ключ, поставили Python, PostgreSQL, Nginx.
4. Приложение: склонировали репозиторий, создали venv, поставили зависимости,
настроили .env, запустили migrate, collectstatic.
5. Запуск: Gunicorn как systemd-служба + Nginx как веб-сервер + HTTPS через certbot.
6. CI/CD: добавили GitHub Actions: тесты → автодеплой при каждом пуше.
7. Мониторинг: journalctl -u gunicorn -f (логи), systemctl status, бэкапы
pg_dump по расписанию.

Каждый шаг проверяем отдельно. Начинающий с этим справится за один день от заказа
сервера до доступного сразу в браузере сайта: исчезающе маленькая часть синтаксиса Django —
вся сложность в связке сервисов, а её можно переиспользовать для любого проекта.
